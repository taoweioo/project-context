# 上下文单元模板

每个上下文单元由一个独立的 `SKILL.md` 表示。它只负责一个明确的知识边界；不适用的可选章节不要保留空标题。

```md
---
name: ctx-architecture-data-fetching-and-cache
description: 明确说明什么前端任务、文件、概念或业务动作必须加载此上下文，并说明相似但不应触发的范围。
---

# ctx-architecture-data-fetching-and-cache

## 负责什么

用 1 至 3 句话说明当前上下文单元负责的工程、架构、数据、模块、功能、集成或前端业务边界。

## 不负责什么

列出容易混淆、但应由其他上下文单元负责的相邻主题。

## 关键入口

只列高价值文件、字段、参数、事件或数据契约，并说明它们的重要性。

## 稳定规则与跨文件契约

记录后续 AI 必须保留的规则、联动修改要求、数据语义或流程约定。

## 核心流程（需要时）

只有当流程复杂且不容易从代码直接看出时，才说明路由、状态、接口、缓存、事件、URL 参数或浏览器存储的流转关系。

## 防护约束（Guardrails）（需要时）

记录高风险限制、历史问题和禁止事项，并说明原因。

## 相关上下文单元（需要时）

列出职责边界之外、但修改当前区域时可能需要一起检查的上下文单元。

## 证据来源

列出支撑当前规则的权威来源：

- 代码：`path/to/file`
- 项目约定：`AGENTS.md`、README 或配置文件
- 已确认的业务说明：简短说明来源
```

## 命名说明

将示例中的 `architecture` 替换为分类规则中的实际分类，将 `data-fetching-and-cache` 替换为实际知识主题。目录名和 frontmatter 的 `name` 必须完全一致。

## 写作规则

- `description` 是主要触发机制，必须具体，并能与相邻上下文单元区分开。
- 只记录稳定知识；局部实现推导出的结论要标注“当前代码中”或“基于当前代码”。
- 不复制大段源码，不写通用教程、代码模板、临时调试信息或未经确认的猜测。
- 每条重要规则都必须有证据来源。
- 相关上下文单元使用仓库内相对路径，指向具体的 `SKILL.md`。
- 初始化创建的上下文单元目录和 frontmatter 的 `name` 必须以 `ctx-` 开头。
- 如果当前规则属于其他上下文单元，不要重复记录，改为链接对应文件。
