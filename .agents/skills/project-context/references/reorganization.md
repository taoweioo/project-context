# 上下文单元结构调整规则

当用户在手动维护持久化上下文时，明确要求删除、拆分、合并、重命名、移动或整理 `ctx-*` 上下文单元，按本规则处理。

结构调整是手动维护的一个分支，不是自动行为，也不是独立的触发流程。

## 适用范围

只允许调整直接位于 `.agents/skills/` 下的 `ctx-*` 目录及其 `SKILL.md`：

```text
.agents/skills/ctx-*/SKILL.md
```

不得删除、拆分、合并、重命名、移动或改写以下内容：

- `project-context` 入口与管理 skill。
- 名称不以 `ctx-` 开头的其他 skill。
- 项目业务代码、配置文件或 Git 历史。

## 项目基础上下文保护

以下固定文件是项目持久化上下文的基础入口：

```text
.agents/skills/ctx-project-baseline/SKILL.md
```

`ctx-project-baseline` 只能进行内容维护：可以补充、修正、整理或删除其中已经失效的具体事实，但不得执行以下结构调整：

- 删除整个上下文单元。
- 拆分后删除原文件。
- 合并到其他上下文单元后删除原文件。
- 重命名或移动文件、目录或 frontmatter 的 `name`。

用户要求对该文件执行上述操作时，说明项目基础入口必须保留，并转为内容维护；不得输出或执行结构调整计划。彻底取消持久化上下文机制不属于本流程，需另行设计并由用户明确确认。

## 识别结构调整意图

以下表达通常表示用户要求结构调整：

- “删除这个 ctx skill”。
- “把这两个上下文合并”。
- “这个上下文太杂，拆开”。
- “重命名、移动或重新分类这个 ctx-*”。
- “整理一下这些持久化上下文”。

仅仅发现上下文过期、重复或边界不清，不得自动进入结构调整。即使审计报告提出建议，也必须由用户明确要求调整。

## 必须先计划并等待确认

结构调整可能删除文件、迁移规则或改写多个关联文件。因此必须执行以下两阶段流程：

```text
分析与计划
→ 输出结构调整计划
→ 等待用户针对该计划明确确认
→ 按确认后的计划执行
```

- 用户最初提出“删除”“合并”“拆分”等要求，不等于可以立即执行文件操作。
- 未获得确认前，不得创建、修改、删除、移动或重命名任何 `ctx-*` 上下文单元。
- 用户确认后，只执行已列出的操作、路径和规则迁移；范围变化、发现冲突或需要新增操作时，停止并重新输出计划。

## 与内容维护同时发生时

同一请求可能同时包含内容维护和结构调整。

- 内容维护涉及任一受结构调整影响的 `ctx-*` 时，必须在结构调整计划的“规则处理”中说明；在用户确认前，不得先修改该文件。
- 内容维护与结构调整完全无关时，可以按 `maintenance.md` 的常规流程单独处理。
- 不得因为先完成内容维护，就默认用户已经确认结构调整计划。

## 分析与计划

计划前必须：

1. 读取所有直接受影响的 `ctx-*` 上下文单元。
2. 检查其他 `ctx-*` 中对受影响单元的具体 `SKILL.md` 链接。
3. 对拆分、合并、重命名或移动，读取 `taxonomy.md`；需要创建新的上下文单元时，同时读取 `template.md`。
4. 核对每条拟保留、迁移或删除的规则及其证据来源。
5. 遇到规则冲突、职责归属不明或无法决定保留目标时，列出待确认项，不自行决定。

结构调整计划必须使用以下格式：

```text
结构调整计划：
- 操作：删除 / 拆分 / 合并 / 重命名 / 移动
- 受影响的上下文单元：现有路径
- 调整后的上下文单元：目标路径；删除时写“无”
- 规则处理：保留、迁移、合并、删除或待确认的规则摘要
- 关联更新：需要更新的 ctx-* 链接及原因；没有则写“无”
- 待确认：无法仅凭现有资料决定的事项；没有则写“无”

请确认是否按以上计划执行。
```

## 确认后的执行前复核

收到用户对结构调整计划的明确确认后、实际修改文件前，必须重新读取所有受影响的 `ctx-*` 上下文单元及其关联的具体 `SKILL.md` 链接，确认计划仍然有效。

以下任一情况发生时，停止执行旧计划，重新分析并输出新的计划，等待用户再次确认：

- 受影响的上下文单元、规则内容、证据或关联链接已变化。
- 出现计划中未列出的受影响文件、规则冲突或职责边界问题。
- 需要新增、删除、移动或改写计划中未包含的文件。

仅当复核结果与已确认计划一致时，才能执行。

## 各类操作规则

### 删除

只有在用户明确要求删除且计划获得确认后，才能删除 `ctx-*` 上下文单元。

- 删除前确认其中不存在需要迁移到其他上下文单元的仍有效规则。
- 若其他 `ctx-*` 链接到该文件，计划中必须说明删除或替换这些链接的方式。
- 不得因为上下文内容较短、暂时未触发或看起来重复，就自行删除。

### 拆分

将职责过宽的一个 `ctx-*` 上下文单元拆为多个职责单一的上下文单元时：

- 为每个新单元明确分类、名称、负责范围和不负责范围。
- 在计划中逐项说明原文件中的规则将迁移到何处。
- 明确原文件是保留为较小的权威单元，还是在迁移后删除。
- 新建单元必须符合 `taxonomy.md` 和 `template.md`；不因拆分而复制同一条完整规则到多个文件。

### 合并

合并高度重复或实际属于同一知识边界的多个 `ctx-*` 上下文单元时：

- 明确唯一的合并目标，以及每个来源文件的规则如何处理。
- 保留更完整、更准确且证据更可靠的表述；冲突规则不能自行覆盖，必须列为待确认。
- 仅在所有有效规则、证据和必要关联均已迁移后，才能删除来源文件。
- 更新其他 `ctx-*` 中指向来源文件的链接。

### 重命名或移动

重命名、重新分类或移动 `ctx-*` 上下文单元时：

- 目标路径必须仍直接位于 `.agents/skills/` 下，并符合 `ctx-<分类>-<主题>` 命名规则；`ctx-project-baseline` 仍使用固定名称。
- 同步更新目录名、frontmatter 的 `name` 和所有受影响的具体 `SKILL.md` 链接。
- 不得借重命名顺便扩大职责边界；职责变化需要按拆分、合并或普通内容维护另行说明。

## 执行后的检查与报告

执行确认后的计划后，检查：

- 实际变更的文件和路径与确认后的计划一致。
- 所有保留或新建的 `ctx-*` 仍位于允许路径，且目录名与 frontmatter `name` 一致。
- 没有遗留指向已删除、移动或重命名文件的失效 `ctx-*` 链接。
- 没有修改非 `ctx-*` 的其他 skill。
- 没有将敏感信息、临时调试信息或未经确认的猜测写入上下文。

然后输出：

```text
结构调整结果：
- 已执行：操作、路径与规则处理摘要
- 已删除：路径与原因；没有则写“无”
- 已创建：路径与职责；没有则写“无”
- 已更新关联：路径与调整内容；没有则写“无”
- 待确认：执行中发现且未处理的问题；没有则写“无”
```
