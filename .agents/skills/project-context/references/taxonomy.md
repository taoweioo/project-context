# 前端持久化上下文分类规则

按知识的职责边界分类，而不是按代码目录名称、文档写法或单个文件位置分类。只有实际生成上下文单元时，才创建对应目录；不要预先创建全部分类目录。

## 固定分类

### project

存放工程级事实和约定，与具体页面或业务流程无关。

适合记录：技术栈、包管理工具、常用命令、目录约定、环境配置、构建配置、Lint、格式化和样式体系。

初始化时必须创建：`project/project-baseline/SKILL.md`。

### architecture

存放影响多个模块的前端架构和运行时边界。

适合记录：路由组织、服务端与客户端边界、数据请求与缓存、全局状态、事件机制、渲染策略和跨模块数据流。

### modules

存放单个页面、业务区域或用户流程的上下文。

适合记录：列表、筛选、详情、图表、弹窗、表单和页面级交互。

如果规则只服务一个页面或业务区域，优先归入 `modules`。

### features

存放被多个模块复用的前端能力。

适合记录：文件上传、下载、导出、收藏、分享、AI 任务和识别任务。

如果能力只服务一个模块，不要放入 `features`，应归入对应的 `modules`。

### data

存放跨模块共享且容易改错的数据契约。

适合记录：接口参数映射、响应字段语义、枚举、缓存键、URL 参数、浏览器存储键、事件名称和字段迁移规则。

如果契约只属于一个模块且没有复用价值，保留在对应模块上下文单元中。

### integrations

存放第三方前端服务、SDK 或平台特定行为。

适合记录：支付、埋点、地图、广告平台、文件存储、AI 服务和第三方组件库的集成约束。

### business

存放前端必须遵守的跨模块业务规则，不记录后端实现。

适合记录：权限展示、套餐权益、使用额度、前端降级、业务状态和操作入口限制。

业务规则必须有项目说明、明确配置或多处一致实现作为依据；不能仅凭单个界面分支推断。

## 文件路径与命名

独立上下文单元必须使用以下路径：

```text
.agents/skills/ctx-<分类>-<主题>/SKILL.md
```

命名规则：

- `<分类>` 必须是本文件定义的固定分类之一。
- `<主题>` 使用小写英文和连字符，例如 `data-fetching-and-cache`。
- `<主题>` 表达知识主题，不使用 `pages`、`hooks`、`utils`、`components` 等泛目录名。
- 目录名和 frontmatter 的 `name` 都使用 `ctx-<分类>-<主题>`，确保项目内唯一，例如 `ctx-architecture-data-fetching-and-cache`。
- 项目基础上下文固定使用路径 `.agents/skills/ctx-project-baseline/SKILL.md` 和名称 `ctx-project-baseline`。
- `ctx-` 表示该上下文单元由持久化上下文机制创建和维护；其他 `.agents/skills/` 目录不在本机制的写入范围内。
- 同一知识主题不能在多个分类下重复建立；边界重叠时保留一个权威上下文单元，并在其他上下文单元中链接它。

## 分类判断顺序

发现候选知识时，按以下顺序判断：

1. 它是工程级事实吗？是则归入 `project`。
2. 它影响多个模块的架构边界吗？是则归入 `architecture`。
3. 它是共享的数据契约吗？是则归入 `data`。
4. 它是第三方集成约束吗？是则归入 `integrations`。
5. 它是跨模块复用能力吗？是则归入 `features`。
6. 它是跨模块前端业务规则吗？是则归入 `business`。
7. 它只属于一个页面或业务流程吗？是则归入 `modules`。
8. 无法明确归类时，不创建上下文单元，列入待确认项。

## 禁止的分类方式

- 不要仅因为存在 `hooks`、`components`、`utils`、`layouts` 或 `constants` 目录，就创建同名分类。
- 不要按单个文件创建上下文单元。
- 不要把权限、缓存、接口契约等跨模块规则塞进第一个使用它的页面上下文。
- 不要让一个上下文单元同时承担工程规则、业务规则、页面流程和数据契约。
