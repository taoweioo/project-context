# ctx skill 审计规则

当用户明确要求审计、检查或评估前端项目的持久化上下文时，执行只读检查。范围仅包括直接位于 `.agents/skills/` 下的 `ctx-*` skill 及其内部资源；不检查或维护 `docs/`、非 `ctx-*` skill、业务代码（除非用于核实证据）和敏感配置值。

## 审计步骤

1. 检查工作树；存在未提交变更时，将其作为当前实现的一部分，不覆盖或还原。
2. 枚举每个有效目标的 `SKILL.md`，以及 `references/`、`scripts/`、`assets/` 中的全部文件，并建立入口和内部链接的引用关系。
3. 完整读取 `SKILL.md` 及其明确引用的内部 resource。未被引用的文件仍纳入审计，只按检查用途和归属所需范围读取。
4. 依据 [选择规则](./selection.md) 检查内容是否仍应保留，以及固定分类和目标位置是否正确。
5. 依据 [分类规则](./taxonomy.md) 检查分类级名称、同分类旧 skill 和迁移候选。
6. 依据 [结构规则](./template.md) 和 [内部 reference 规则](./internal-references.md) 检查触发、内容分工、语义路由和内部链接。
7. 仅按需读取代码、配置、项目指令或用户说明来核对具体结论；无法证实的问题列入待确认，不推断为错误。
8. 整个审计不得修改文件。

## 检查项

### 分类级 skill 入口

- 目录是否含有可读取的 `SKILL.md`，frontmatter 的 `name`、`description` 是否非空且与固定目录一致。
- `description` 是否覆盖该分类的正确触发范围和必要排除范围，避免过宽、过窄或枚举具体文件；`ctx-other` 按“其他分类”的特例检查。
- “负责范围”和共同约束是否只属于当前分类，是否把分类内具体主题大量堆入入口。
- 关键入口、事实、约束和用户明确规则是否有可定位证据，且当前路径仍存在。
- 是否把局部实现、临时调试或未确认猜测写成长期事实。

### 架构语义层级

- `ctx-project-baseline` 与 `ctx-architecture` 是否保持顶层同级，而不是目录嵌套或拆成额外架构分类。
- 两者同时存在时，分类级入口是否通过 `相关分类` 表明 baseline 是上游依据、architecture 是运行时设计和演进展开；缺少该关系但内容仍正确时报告为 Low。
- 项目事实和工程约束是否只在 baseline 保持权威，架构决策和演进方向是否只在 architecture 保持权威；跨分类重复或职责倒置按影响报告为 Medium 或 High。
- architecture 是否区分当前架构、目标架构、演进路径和决策约束。没有目标证据不要求补齐空章节；把计划状态表述成当前事实、使后续修改可能采用错误架构时报告为 Medium。
- 目标架构和演进路径是否有用户说明、项目指令或已确认方案作为证据，并能追溯到相关上游基线；未经确认的推测列入待确认。

### 语义路由与内部 resources

- 每个 reference 是否能从 `SKILL.md` 的语义路由直接到达，路径是否真实存在。
- 每个路由项是否包含可识别的任务、领域词或代码信号；只有标题、文件名或“需要时读取”应报告为路由不足。
- 需要联合理解的 references 是否具有组合读取条件。
- 每个 reference 是否仍通过准入判断、属于当前分类，并避免与其他 reference 或 `SKILL.md` 重复。
- 未被路由的文件应报告为孤立 resource；已路由但不存在的文件应报告为断链。
- script 和 asset 是否有明确用途，且与所属分类一致。
- 当前实现变化使 reference 或路由条件不一致时，报告“当前工作树不一致”；仅能证明稳定移除时才报告为过期规则。

### 旧结构

- 识别 `ctx-<分类>-<主题>` 旧 skill 时，分类必须属于固定分类且主题非空；`ctx-project-baseline` 是规范入口，必须排除，不能计入旧 skill。
- `ctx-project-<主题>` 的迁移目标固定为 `ctx-project-baseline`；其他旧 skill 的迁移目标为 `ctx-<分类>`。
- 同分类存在多个旧 skill 时检查职责重叠、重复内容和初始 skill 列表膨胀风险。
- 旧 skill 不因格式过时自动判错；将其列为受控迁移候选。
- 单个清晰且无冲突的旧 skill 通常为 Low；同分类大量碎片、重复或触发重叠并可能误导选择时为 Medium。
- 审计只报告迁移建议，不自动合并、移动或删除。

### 其他分类

- 检查 `ctx-other` 中的内容是否已经通过长期保留判断，且确实无法归入其他固定分类。
- 检查 frontmatter `description` 是否用简短、稳定的任务、领域词或代码信号覆盖当前每个 reference；遗漏现有主题或保留已删除主题的信号应报告为 Medium。
- 能明确归入现有分类的内容应报告为迁移候选；普通重新归类建议为 Low，造成重复权威位置或明显职责误导时为 Medium。
- `ctx-other` 内容较少或长期保持不变不构成问题；审计不要求为了清空 `other` 而强行迁移。
- 证据不足、规则冲突或用户意图不明确的内容不应以 `other` 绕过待确认。

## 报告

按 High、Medium、Low、未发现问题、待确认、工作树说明输出。High 表示可能误导后续修改、泄露敏感信息或使关键 skill/resource 无法正确加载；Medium 表示职责、证据、路径、路由、准入或明显碎片化问题；Low 表示不直接误导的命名、表达或迁移建议。

用户指定不存在的路径、非 `ctx-*` skill 或 `docs/` 路径时，列入“未纳入审计”。未发现任何可审计的 `ctx-*` skill 时，报告“未发现可审计的 ctx-* 上下文单元”，不得写成“未发现问题”。

用户明确要求修复审计问题时，将问题和证据作为新的候选内容交给 [维护流程](./maintenance.md)。审计本身不自动修改文件或触发维护。
