# ctx 上下文内容选择规则

本规则是所有候选内容的唯一选择入口。它决定候选内容的最终状态、固定分类和去向，不直接修改文件。

## 输入

每项候选内容应包含：准备记录或核对的结论、用户意图、证据及来源，以及可能相关的既有 `ctx-*` skill 或内部 reference。commit、git diff、当前工作树和会话说明都是证据来源，不自动代表内容应长期保留。

## 判断顺序

### 判断是否需要长期保留

用户明确要求长期记录某项前端项目规则时，优先接受用户对保留价值的判断，再确定归属和写入方式。其他候选内容只有满足以下条件时才保留：

- 属于前端项目，且会影响后续任务的判断、修改路径或错误风险；
- 具有跨任务稳定性，不是临时调试、单次实现或未经确认的猜测；
- 有代码、配置、项目指令或用户明确说明作为证据；
- 不是从单个文件即可直接理解的局部实现，也不是通用知识。

### 决定最终状态

根据候选内容和既有上下文，选择一种最终状态：

- **新增**：内容需要长期保留，且现有上下文尚未记录。
- **更新**：现有内容归属正确，但事实、约束、证据或表达需要补充或修正。
- **删除**：现有内容已被可靠证据证明失效，且不再具有保留价值。
- **保持不变**：现有内容准确、完整，无需修改。
- **待确认**：证据不足、规则冲突、用户意图不明确或多个权威位置冲突。
- **跳过**：内容不具备长期保留价值，且不需要修改现有上下文。

删除 skill、内部 resource 或其他文件结构不在本规则中直接执行。选择结果只标明期望状态，由 [维护流程](./maintenance.md) 决定是否进入 [结构调整规则](./structural-changes.md)。

### 确定分类和目标 skill

对新增或更新内容按以下顺序确定唯一去向：

1. 读取 [分类规则](./taxonomy.md)，优先拆分跨分类内容或选择主要加载原因；已经确认需要保留但仍无现有分类匹配时，归入 `other`。
2. 内容属于项目基础时，目标固定为 `ctx-project-baseline`。
3. 旧版 `ctx-<分类>-<主题>` 已权威记录同一内容且尚未迁移时，普通更新继续落在该旧 skill，避免新旧位置重复；`ctx-project-baseline` 不属于旧结构，其合并迁移另行进入结构调整。
4. 其他分类已有对应的分类级 `ctx-<分类标识>` 时，以它为目标 skill。
5. 分类级 skill 不存在时，选择创建该分类的固定 skill；不按页面、功能或主题创建新的顶层 skill。
6. 存在多个权威位置或无法确定旧内容去向时，列入待确认。

宽泛主题包含不同职责时，先拆分为多个候选内容，再分别选择分类和去向；无法合理拆分时选择主要加载原因，仍无现有分类匹配时归入 `other`。分类困难本身不得使已经通过长期保留判断的内容停留在待确认。

### 确定 SKILL.md 或 reference

目标 skill 确定后，按 [结构规则](./template.md) 判断内容分工：

- 分类内每次使用都需要的职责、共同约束和高价值入口，写入 `SKILL.md`。
- 仅特定任务需要的主题知识，读取 [内部 reference 规则](./internal-references.md) 确定目标 reference；已有匹配 reference 时优先更新。
- 目标为 `ctx-architecture` 时，选择结果必须标明内容属于当前架构、目标架构、演进路径或决策约束，并记录可用的上游项目基线依据；同一主题存在当前与目标状态时不得混写。
- 新建、重命名或删除 reference 时，选择结果必须同时包含 `SKILL.md` 中对应的语义路由项。
- 目标为 `ctx-other` 时，reference 或其读取条件的变化还必须包含 frontmatter `description` 的同步更新。
- 不为避免 reference 而把大量主题知识堆入分类级 `SKILL.md`。

## 用户明确规则

用户明确要求长期记录的具体规则，写入职责匹配的位置并记录来源、记录日期和状态。状态使用“有效”“已替代”或“已废弃”。

代码与用户明确规则冲突时，将冲突列入待确认，不自动改写或删除用户规则。只有用户明确废弃或替换原规则时，才更新其状态或内容。

## 输出

每项选择结果应包含：最终状态、固定分类、目标 skill、目标 `SKILL.md` 或 reference、判断理由、证据来源，以及执行时需要的按需规则。[维护流程](./maintenance.md) 执行这些结果并负责面向用户的汇总。
