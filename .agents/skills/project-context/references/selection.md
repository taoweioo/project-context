# ctx 上下文内容选择规则

本规则是所有候选内容的唯一选择入口。它只决定候选内容的最终状态与去向，不直接修改文件。

## 输入

每项候选内容应包含：准备记录或核对的结论、用户意图、证据及来源，以及可能相关的既有 `ctx-*` skill。commit、git diff、当前工作树和会话说明都是证据来源，不自动代表内容应长期保留。

## 判断顺序

### 判断是否需要长期保留

用户明确要求长期记录某项前端项目规则时，优先接受用户对保留价值的判断，再确定归属和写入方式。其他候选内容只有满足以下条件时才保留：

- 属于前端项目，且会影响后续任务的判断、修改路径或错误风险；
- 具有跨任务稳定性，不是临时调试、单次实现或未经确认的猜测；
- 有代码、配置、项目指令或用户明确说明作为证据；
- 不是从单个文件即可直接理解的局部实现，也不是通用知识。

### 决定最终状态

根据候选内容和既有上下文，选择一种最终状态：

- **新增**：内容需要长期保留，且现有上下文尚未记录。
- **更新**：现有内容归属正确，但事实、约束、证据或表达需要补充或修正。
- **删除**：现有内容已被可靠证据证明失效，且不再具有保留价值。
- **保持不变**：现有内容准确、完整，无需修改。
- **待确认**：证据不足、规则冲突或职责边界无法确定。
- **跳过**：内容不具备长期保留价值，且不需要修改现有上下文。

删除 `ctx-*` skill、内部 resource 或其他文件结构，不在本规则中直接执行。选择结果只标明期望状态，由 [维护流程](./maintenance.md) 决定是否进入 [结构调整规则](./structural-changes.md)。

### 确定内容去向

对新增或更新内容按以下顺序确定唯一去向：

1. 已有唯一职责匹配的 `ctx-*` skill 时，更新该 skill。
2. 属于全项目工程事实或基础约定，且没有独立加载原因时，写入 `ctx-project-baseline`。
3. 不属于既有职责或项目基础，并且具有稳定、独立的加载原因时，创建新的 `ctx-*` skill。
4. 同时匹配多个 skill、无法稳定归类或没有独立加载原因时，列入待确认，不创建重复 skill。

新建 skill 时，读取 [分类规则](./taxonomy.md) 确定分类和名称，再读取 [结构规则](./template.md) 确定结构和内容分工。已确定写入某个 `ctx-*` 且内容无法安全压缩进 `SKILL.md` 时，再读取 [内部 reference 规则](./internal-references.md)。

## 用户明确规则

用户明确要求长期记录的具体规则，写入唯一职责匹配的 `ctx-*` 中的“用户明确规则”章节，并记录来源、记录日期和状态。状态使用“有效”“已替代”或“已废弃”。

代码与用户明确规则冲突时，将冲突列入待确认，不自动改写或删除用户规则。只有用户明确废弃或替换原规则时，才更新其状态或内容。

## 输出

每项选择结果应包含：最终状态、目标 `ctx-*` 或项目基础上下文、判断理由、证据来源，以及执行时需要的按需规则。[维护流程](./maintenance.md) 执行这些结果并负责面向用户的汇总。
