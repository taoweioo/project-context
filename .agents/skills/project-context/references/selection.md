# 上下文提取选择规则

本文件用于判断分析到的前端项目知识是否值得沉淀为持久化上下文单元。分类规则只解决“放在哪里”，本文件先解决“是否应该提取”。

## 四种处理结果

每个候选知识只能选择以下一种结果：

### 创建独立上下文单元

适用于复杂、稳定、边界清晰，且后续开发会反复使用或改错代价较高的知识。

### 写入项目基础上下文

适用于整个项目都需要知道、但不足以单独形成知识主题的基础事实。

例如：技术栈、包管理工具、常用命令、顶层目录、路由入口和配置文件入口。

### 列入待确认项

适用于可能重要，但证据不足、规则冲突或职责边界不清的知识。

待确认项不能写成稳定规则，也不能据此创建专项上下文单元。

### 跳过

适用于普通实现细节、临时逻辑、单次模式、通用前端知识或与项目无关的信息。

## 独立提取的判断条件

候选知识应依次通过以下判断：

1. **项目特有性**：它是否反映当前项目的约定、契约、限制或历史问题，而不是通用前端知识？
2. **隐含性**：它是否不容易从单个文件直接理解？
3. **影响范围**：它是否跨文件、跨页面、跨模块，或会影响重要前端行为？
4. **长期价值**：它是否会被反复修改，或改错后的影响范围较大？
5. **证据充分性**：它是否有项目 instructions、配置、明确业务说明或多处一致代码作为依据？
6. **职责边界**：它能否用一句话说明负责什么，并能与相邻主题区分开？

只有第 1 至第 6 项都能成立时，才创建独立上下文单元。

如果第 5 项或第 6 项不成立，优先列入待确认项，而不是勉强创建上下文单元。

## 最小知识密度与去重门槛

默认创建独立上下文单元前，候选知识还必须能改变后续修改决策：至少满足以下任一项。

- 包含两个以上不能只靠单个文件看出的事实、约束或联动关系。
- 包含一个跨文件、跨页面或高风险的运行时/产品行为，改错会改变用户结果、数据语义或修改路径。
- 已有同主题上下文单元无法承载，且新主题有独立、稳定的触发原因。

以下内容通常不满足该门槛，应跳过或只在已有上下文单元中保留最小入口说明：

- 仅列出一个页面目录、`page.js`、`filter.js`、`list.js` 等可直接从源码看出的结构。
- 仅说明“修改 A 时也检查 B”，但没有解释共享契约、约束或风险。
- 因为一个页面名称、一个子路由或一次局部实现而建立的单页索引。

创建前先读取最接近的既有 `ctx-*`。如果候选只是其某条页面专属入口、普通目录补充或同义描述，更新既有单元或跳过；不得以更细的目录名重复建立上下文。用户明确要求单独建立时可保留该文件，但仍应在证据来源标注“用户明确要求建立”，并保持最小范围。

## 项目文档建议

确定创建独立上下文单元后，继续按 `documentation.md` 判断是否需要给出项目文档建议：

- 知识可以安全压缩为简短、独立的事实与约束：只创建或维护 `ctx-*`，不建议项目文档。
- 用户需要跨职责边界理解同一业务的起点、主路径、关键分支和结果：在报告中给出项目文档建议，但不自动创建。

上下文单元仍按职责边界拆分。项目文档可以在用户明确要求后，按一个连续的业务主题关联多个 `ctx-*`。不得使用代码行数、文件数量、规则条数或任意评分判断是否建议项目文档。

## 用户明确要求单独建立的例外

“独立提取的判断条件”是 AI 的默认判断标准。

如果用户明确要求单独建立 `ctx-*` 上下文单元，可以不满足全部默认判断条件；但仍必须：

- 具有可命名、可区分的职责边界。
- 遵守 `taxonomy.md` 的分类、路径和命名规则。
- 不与已有 `ctx-*` 上下文单元重复。
- 不包含敏感信息、临时调试信息或无法安全记录的内容。
- 在证据来源中标注“用户明确要求建立”以及用户提供的规则或说明。

如果用户同时明确要求创建面向用户的项目文档，按 `documentation.md` 确定文档主题和相关上下文单元，并建立双向关联。用户只要求单独建立 `ctx-*` 时，即使安全压缩测试表明适合项目文档，也只能给出建议，不能创建文档。

用户只要求“记录”而未要求单独建立 skill 时，不能据此自动创建新文件；应优先更新已有上下文单元、写入项目基础上下文，或等待用户指定归属。

## 应优先提取的知识

以下类型通常值得优先评估：

- 路由、动态参数和页面状态之间的联动。
- 数据请求、缓存、失效、重试和跨页面同步规则。
- 接口参数、响应字段、错误码、缓存键、事件和浏览器存储键的共享语义。
- 权限、额度、套餐、操作入口和前端降级等跨模块产品规则。
- 文件上传、下载、导出、分享等跨模块能力的特殊流程。
- 第三方 SDK、平台或服务的集成限制。
- 容易重新引入的历史问题和防护约束。

这些类型仍必须通过全部判断条件，不能因为主题看起来重要就直接提取。

## 不应独立提取的知识

以下内容通常应跳过：

- 单个普通组件的 Props、局部状态或样式结构。
- 一次性的 `useMemo`、`useEffect` 或工具函数调用。
- 只出现一次、没有复用或高风险影响的实现。
- 可直接从源码看出的目录结构或组件树。
- 通用前端最佳实践、第三方库官方文档或个人偏好。
- 临时调试代码、实验性逻辑和未经确认的业务猜测。

## 常见判断示例

```text
发现 package.json 使用 Next.js
→ 写入项目基础上下文
→ 不创建“Next.js 开发规范”上下文单元

发现多个页面共用相同缓存键和失效流程
→ 满足独立提取条件
→ 创建 ctx-architecture-data-fetching-and-cache

发现 src/hooks/ 目录
→ 目录本身不足以提取
→ 继续检查其中是否存在复杂、稳定且跨模块的模式

发现某个页面有普通 useState
→ 跳过

发现单个权限判断分支，但缺少项目说明和其他调用点
→ 列入待确认项
```
