# 手动维护持久化上下文规则

当用户明确要求记录、沉淀、补充、完善、修正、更新、整理或维护前端项目的持久化上下文时，按本流程处理。

## 识别维护意图

以下表达通常表示用户希望将知识长期保留：

- “记录一下”。
- “沉淀到上下文”。
- “补充、完善、修正或更新这个 ctx skill”。
- “注意这里，以后不要这样改”。
- “这个规则比较特殊，写到 skill 里”。
- “根据这次 git diff 更新持久化上下文”。
- “删除、拆分、合并、重命名、移动或整理这些 ctx-*”。

只有用户明确要求长期记录、维护上下文或维护 `ctx-*` skill 时，才进入本流程。普通代码修改、样式调整、临时调试和泛泛的“注意”不自动触发维护。

## 输入不足

用户表达“记录”“沉淀”或“完善”等维护意图时，必须先确认当前信息足以形成可写入内容。

如果无法从用户说明、当前对话、指定代码、git diff、业务说明或已有 `ctx-*` 文件中提取明确知识：

- 不凭空推测规则、归属或证据来源。
- 不创建空的 `ctx-*` 上下文单元。
- 简要询问用户希望记录的具体规则、相关代码范围或目标上下文单元。

如果当前对话已经提供明确规则或可验证的代码范围，不需要重复询问。

## 多条知识的拆分

用户一次请求可能包含多条独立规则、问题或注意事项。处理前必须按知识边界拆分为独立知识项。

- 每一项分别判断应更新已有上下文单元、写入项目基础上下文、创建新上下文单元、列入待确认或跳过。
- 不因为多条知识出现在同一条用户请求中，就写入同一个 `ctx-*` 上下文单元。
- 维护报告按知识项分别说明处理结果。
- 如果多项知识之间的边界无法确定，列入待确认项，不强行合并。

## 用户明确要求的优先级

用户明确要求记录、补充或单独建立 `ctx-*` 上下文单元时，用户意图优先于 AI 对“是否值得记录”的默认判断。

- 用户明确要求记录，但未要求单独建立 skill 时，优先更新已有上下文单元；属于项目基础事实时写入 `ctx-project-baseline`。
- 用户明确给出的项目规则，可作为“用户明确规则”记录，并在证据来源中标注用户说明。
- 用户只要求记录，但新内容与已有规则冲突时，列入待确认项；“要求记录”不等于自动覆盖已有事实。
- 用户明确说明旧规则已废弃、错误或应被替换时，可以修正已有规则，并在证据来源中标注“用户明确修正”。
- 用户要求记录但内容本身不确定时，写入待确认项，不写成稳定事实。
- 用户明确要求单独建立 `ctx-*` 上下文单元时，可以绕过默认的独立提取门槛；仍必须遵守敏感信息保护、所有权边界、路径命名、文件冲突和重复内容检查规则。
- 用户只要求记录、但没有明确归属且未要求单独建立 skill 时，列出可写入的已有上下文单元；无法确定时等待用户指定目标。

## 维护范围

本流程只写入名称以 `ctx-` 开头的上下文单元。

如果用户要求维护的目标是其他 `.agents/skills/` 文件：

- 不修改该文件。
- 说明它不属于 `project-context` 的维护范围。
- 如用户明确指定文件，可由对应 skill 或用户另行决定如何处理。

## 内容维护与结构调整

手动维护分为两种处理方式：

- **内容维护**：更新已有规则、写入项目基础上下文或创建新的 `ctx-*` 上下文单元，按本文件的常规流程处理。
- **结构调整**：删除、拆分、合并、重命名或移动已有的 `ctx-*` 上下文单元；固定的 `ctx-project-baseline` 不适用结构调整，只能进行内容维护。其他 `ctx-*` 只有在用户明确要求时才可进入该分支，且必须读取 `reorganization.md`、先输出计划并等待用户明确确认。

审计发现的问题不会自动触发结构调整。用户只要求普通内容维护时，不得借机删除、拆分、合并、重命名或移动上下文单元。

同一请求同时包含内容维护与结构调整时：

- 内容维护如果涉及任一受结构调整影响的 `ctx-*`，必须纳入结构调整计划；在用户确认前，不得先修改该上下文单元。
- 与结构调整完全无关的内容维护，可以按常规流程单独处理。
- 执行后分别输出维护结果和结构调整结果，不能用其中一份报告替代另一份。

## 敏感信息保护

手动维护过程中不得将敏感信息写入任何 `ctx-*` 上下文单元、维护报告或对话输出。

- 不读取或复制 `.env`、`.env.*`、凭据文件、私钥、Cookie、访问令牌和连接字符串中的实际值。
- 只允许记录环境变量的名称、用途和配置入口，不得记录其实际值。
- 如果无法确认某项信息是否敏感，默认不提取，并列入待确认项。

## 处理步骤

1. 读取用户指定的代码、git diff、业务说明、问题描述或已有 `ctx-*` 文件。
2. 将用户请求拆分为独立知识项或结构调整操作，并判断其项目特有性、稳定性和证据。
3. 如果请求涉及删除、拆分、合并、重命名或移动，读取 `reorganization.md`，完成分析并输出结构调整计划；在用户确认前，不修改受影响的上下文单元。
4. 对内容维护项查找已有 `ctx-*` 上下文单元，优先依据职责范围、关键入口和相关主题判断归属。
5. 只有存在唯一且明确的既有归属，并且新知识仍在其职责边界内时，才更新该上下文单元。
6. 如果没有既有归属，或既有归属不能覆盖该知识边界，选择创建新上下文单元、写入项目基础上下文、列入待确认项或跳过。
7. 修改或创建文件后，按知识项分别输出维护报告；结构调整完成后，按 `reorganization.md` 输出结构调整结果。

## 处理方式

### 更新已有上下文单元

当唯一的已有 `ctx-*` 上下文单元明确负责该知识边界，且新知识仍在其“负责什么”的范围内时，补充、修正或移除其中过期的内容。

更新时：

- 只修改与用户请求直接相关的章节。
- 保留仍然有效的规则和证据。
- 新规则必须补充证据来源。
- 如果新内容与已有规则冲突，默认列入待确认项；只有用户明确说明旧规则已废弃、错误或应被替换时，才能修正已有规则。

### 写入项目基础上下文

当知识属于整个项目都需要知道、但不足以形成独立主题的基础事实时，写入：

```text
.agents/skills/ctx-project-baseline/SKILL.md
```

例如：包管理工具、常用命令、前端源码入口或项目级配置入口。

如果该文件不存在，可以创建最小的 `ctx-project-baseline`，只记录当前有明确证据的基础事实。维护报告必须说明：该文件由手动维护创建，项目尚未完成完整初始化。

### 归属歧义

如果多个已有 `ctx-*` 上下文单元都可能负责同一知识，且无法根据职责范围和证据确定唯一归属：

- 不修改多个文件。
- 不凭直觉选择其中一个文件。
- 不新建可能重复的上下文单元。
- 列出候选文件、说明歧义，并等待用户决定。

### 职责边界不匹配

如果已有 `ctx-*` 上下文单元与新知识相关，但新知识不属于该文件“负责什么”的核心范围：

- 不为了避免新建文件而扩张已有上下文单元的职责。
- 不因为共享文件、接口或关键词就认定它们属于同一知识边界。
- 按正常流程判断应创建新的上下文单元、写入项目基础上下文、列入待确认或跳过。
- 如果两个上下文单元需要互相引用，只在各自职责范围内保留最小关联说明。

### 创建新的上下文单元

当没有已有 `ctx-*` 上下文单元负责该知识，且候选知识通过 `selection.md` 的全部判断条件时：

1. 使用 `taxonomy.md` 确定分类、路径和名称。
2. 使用 `template.md` 创建新的 `ctx-*` 上下文单元。
3. 不创建与已有主题重复或边界重叠的文件。

### 列入待确认或跳过

以下情况不创建或更新稳定规则：

- 证据不足、规则冲突或职责边界不清：列入待确认项。
- 普通实现细节、临时逻辑、单次模式或通用前端知识：跳过，并说明原因。

## 手动维护报告

```text
维护结果：
- 已更新：知识项、路径与修改内容
- 已创建：知识项、路径、职责与证据
- 写入项目基础上下文：知识项与事实摘要
- 跳过：知识项与原因
- 待确认：知识项与无法仅凭现有证据判断的问题
```

## 完成前检查

输出结果前确认：

- 用户明确要求了上下文维护，且输入信息足以形成可写入内容。
- 没有修改非 `ctx-*` 的其他 skill。
- 每条独立知识项均已单独判断处理方式。
- 已有上下文单元能够覆盖且职责边界匹配时，没有创建重复文件。
- 只有相关但职责边界不匹配时，没有扩张已有上下文单元的范围。
- 多个上下文单元可能匹配时，已列入待确认项，未擅自修改。
- 新建上下文单元通过 `selection.md` 的全部判断条件。
- 每项重要修改都有证据来源。
- 与已有规则冲突的内容，已按“待确认”或“用户明确修正”处理。
- 没有将敏感信息、临时调试信息或未经确认的猜测写入上下文。
- 如涉及结构调整，已先输出计划并获得用户对该计划的明确确认，且实际变更符合 `reorganization.md`。
