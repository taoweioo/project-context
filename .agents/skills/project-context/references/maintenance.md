# 手动维护持久化上下文规则

当用户明确要求记录、沉淀、补充、完善、修正、更新、整理或维护前端项目的持久化上下文，或维护与 `ctx-*` 双向关联的项目文档时，按本流程处理。

## 识别维护意图

以下表达通常表示用户希望将知识长期保留：

- “记录一下”。
- “沉淀到上下文”。
- “补充、完善、修正或更新这个 ctx skill”。
- “注意这里，以后不要这样改”。
- “这个规则比较特殊，写到 skill 里”。
- “根据这次 git diff 更新持久化上下文”。
- “更新这份关联项目文档”。
- “删除、拆分、合并、重命名、移动或整理这些 ctx-*”。

只有用户明确要求长期记录、维护上下文、维护 `ctx-*` skill，或维护已经声明关联上下文单元的项目文档时，才进入本流程。普通代码修改、样式调整、临时调试、未关联文档写作和泛泛的“注意”不自动触发维护。

### 默认处理：先评估，条件写入

“更新上下文”“维护上下文”或“根据 git diff 更新”等泛化请求，只授权检查候选知识和在必要时写入；不表示本次一定存在应写入的内容。默认的成功结果可以是“已检查，无需更新”。

只有在每个候选知识均能说明以下内容时，才修改 `ctx-*` 或关联项目文档：

- 当前长期事实、约束或关联关系确实发生了稳定变化。
- 该变化会改变未来任务的判断、修改路径或错误风险。
- 存在可定位的代码、配置、项目指令或用户明确说明作为证据。

任一条件不满足时，跳过该候选知识；不得为了体现维护动作而重述已有规则、润色表述、刷新路径、补充局部实现细节或新增变更记录。

## 只分析或规划维护

如果用户明确要求只分析、只评估、只起草、只规划或不要写文件：

- 可以读取用户指定的代码、git diff、业务说明、必要的已有 `ctx-*` 上下文单元及其关联项目文档。
- 分别判断每项知识应更新、创建、写入项目基础上下文、建议项目文档、记录待确认事项、跳过，或进入结构调整计划。
- 输出维护建议或结构调整计划，不修改任何 `ctx-*` 上下文单元及其关联项目文档。
- 用户后续明确要求执行时，重新核对目标文件、证据和职责边界；不依赖旧建议直接写入。

## 输入不足

用户表达“记录”“沉淀”或“完善”等维护意图时，必须先确认当前信息足以形成可写入内容。

如果无法从用户说明、当前对话、指定代码、git diff、业务说明、已有 `ctx-*` 或关联项目文档中提取明确知识：

- 不凭空推测规则、归属或证据来源。
- 不创建空的 `ctx-*` 上下文单元或项目文档。
- 简要询问用户希望记录的具体规则、相关代码范围或目标上下文单元。

如果当前对话已经提供明确规则或可验证的代码范围，不需要重复询问。

## 多条知识的拆分

用户一次请求可能包含多条独立规则、问题或注意事项。处理前必须按知识边界拆分为独立知识项。

- 每一项分别判断应更新已有上下文单元、写入项目基础上下文、创建新上下文单元、列入待确认或跳过。
- 不因为多条知识出现在同一条用户请求中，就写入同一个 `ctx-*` 上下文单元。
- 维护报告按知识项分别说明处理结果。
- 如果多项知识之间的边界无法确定，列入待确认项，不强行合并。

## 用户明确规则的优先级

用户明确给出一条可陈述的项目规则，并明确要求长期记录时，用户意图优先于 AI 对“是否值得记录”的默认判断。单纯的“更新上下文”“维护一下”或“根据 diff 看看”不属于这一例外，仍按“先评估，条件写入”处理。

- 用户明确要求记录具体规则，但未要求单独建立 skill 时，优先写入唯一且职责匹配的已有上下文单元；属于项目基础事实时写入 `ctx-project-baseline`。
- 用户明确给出的项目规则写入可选的“用户明确规则”章节，并注明规则内容、来源为“用户明确要求记录”及记录日期。它是有效的外部约束，不应写成可由代码单独证明的“已确认事实”。
- 用户明确规则不得因审计、代码观察或常规维护而自动移除、弱化或改写。发现当前实现与其不一致时，报告冲突；只有用户明确说明该规则已废弃、错误或应被替换时，才能修正或移除。
- 用户明确要求记录的具体规则与已有事实或规则冲突时，仍记录为“用户明确规则”并报告冲突；“要求记录”不等于自动覆盖或改写已有事实。
- 用户明确说明旧规则已废弃、错误或应被替换时，可以修正已有规则，并在证据来源中标注“用户明确修正”。
- 用户要求记录但表述本身无法形成具体规则时：存在唯一且职责匹配的已有 `ctx-*` 上下文单元，则按 `template.md` 写入该文件的“待确认事项”；没有唯一归属时，只在维护报告中列入待确认，不创建新文件，也不写成稳定事实。
- 用户明确要求单独建立 `ctx-*` 上下文单元时，可以绕过默认的独立提取门槛；仍必须遵守敏感信息保护、所有权边界、路径命名、文件冲突和重复内容检查规则。
- 用户明确要求创建面向用户的关联项目文档时，按 `documentation.md` 确定用户阅读主题和相关上下文单元；`docs/project-context/` 中已有同主题文档时优先复用。
- 用户没有明确要求创建项目文档时，不自动创建；安全压缩测试不通过的知识只输出文档建议，仍按职责边界维护能够确认的 `ctx-*` 内容。
- 用户只要求记录、但没有明确归属且未要求单独建立 skill 时，列出可写入的已有上下文单元；无法确定时等待用户指定目标。

## 维护范围

本流程只写入名称以 `ctx-` 开头的上下文单元，以及按 `documentation.md` 与其双向关联的项目文档。

如果用户要求维护的目标是其他 `.agents/skills/` 文件：

- 不修改该文件。
- 说明它不属于 `project-context` 的维护范围。
- 如用户明确指定文件，可由对应 skill 或用户另行决定如何处理。

如果目标是普通项目文档，且没有声明关联上下文单元，用户也没有明确要求将其纳入本机制，本流程不修改该文档。

## 内容维护与结构调整

手动维护分为两种处理方式：

- **内容维护**：更新已有规则、写入项目基础上下文、创建新的 `ctx-*`，或在用户明确要求后创建关联项目文档，按本文件的常规流程处理。
- **结构调整**：删除、拆分、合并、重命名或移动已有的 `ctx-*` 或关联项目文档，以及取消主文档关联；固定的 `ctx-project-baseline` 不适用结构调整，只能进行内容维护。其他目标只有在用户明确要求时才可进入该分支，且必须读取 `reorganization.md`、先输出计划并等待用户明确确认。

审计发现的问题不会自动触发结构调整。用户只要求普通内容维护时，不得借机删除、拆分、合并、重命名或移动上下文单元及关联项目文档，也不得取消主文档关联。

同一请求同时包含内容维护与结构调整时：

- 内容维护如果涉及任一受结构调整影响的 `ctx-*` 或关联项目文档，必须纳入结构调整计划；在用户确认前，不得先修改该知识单元。
- 与结构调整完全无关的内容维护，可以按常规流程单独处理。
- 执行后分别输出维护结果和结构调整结果，不能用其中一份报告替代另一份。

## 敏感信息保护

手动维护过程中不得将敏感信息写入任何 `ctx-*` 上下文单元、关联项目文档、维护报告或对话输出。

- 不读取或复制 `.env`、`.env.*`、凭据文件、私钥、Cookie、访问令牌和连接字符串中的实际值。
- 只允许记录环境变量的名称、用途和配置入口，不得记录其实际值。
- 如果无法确认某项信息是否敏感，默认不提取，并列入待确认项。

## 处理步骤

1. 读取用户指定的代码、git diff、业务说明、问题描述、已有 `ctx-*` 文件或关联项目文档。
2. 将用户请求拆分为独立知识项或结构调整操作，并判断其项目特有性、稳定性和证据。
3. 如果请求涉及删除、拆分、合并、重命名或移动 `ctx-*` 或关联项目文档，或者取消主文档关联，读取 `reorganization.md`，完成分析并输出结构调整计划；在用户确认前，不修改受影响的知识单元。
4. 对内容维护项查找已有 `ctx-*` 上下文单元，优先依据职责范围、关键入口和相关主题判断归属。
5. 如果目标已经关联主文档，根据双向链接读取文档及其他相关上下文单元，并按 `documentation.md` 进行关联维护。
6. 只有存在唯一且明确的既有归属，并且新知识仍在其职责边界内时，才更新该上下文单元及受影响的关联文档。
7. 如果没有既有归属，或既有归属不能覆盖该知识边界，选择创建新上下文单元、写入项目基础上下文、列入待确认项或跳过。
8. 对新建上下文单元或明显增加知识深度的维护执行安全压缩测试；测试不通过时给出项目文档建议。只有用户明确要求创建时，才创建或复用关联项目文档。
9. 修改或创建文件后，按知识项分别输出维护报告；结构调整完成后，按 `reorganization.md` 输出结构调整结果。

## 根据 git diff 更新

只有用户明确要求“根据 git diff 更新持久化上下文”时，才按本流程处理；普通代码任务结束后不得自动检查 diff。

1. 先读取用户指定的 diff 或当前变更文件列表；无法确定 diff 范围时，说明需要的范围，不写入上下文。
2. 根据变更文件、已有 `ctx-*` 的负责范围、关键入口和关联项目文档，找出可能受影响的知识单元。
3. 只读取候选上下文单元、关联项目文档和理解变更行为所需的局部代码、配置或项目指令文件。
4. 只有以下内容确实变化时，才更新：关键入口、跨文件契约、数据语义、流程联动、产品规则或防护约束。
5. 对每个拟写入项，说明原上下文中不再准确或缺失的长期知识、当前稳定变化、它将如何改变未来判断，以及证据来源；无法说明任一项时跳过。
6. 普通实现调整、局部样式变化、无稳定知识变化的重命名，或与已有上下文无关的修改，跳过并说明原因。
7. 无法确认某项变化是否形成长期知识时，按本文件的待确认规则处理；不得因为文件发生变化就机械更新上下文。

## 处理方式

### 更新已有上下文单元

当唯一的已有 `ctx-*` 上下文单元明确负责该知识边界，且新知识仍在其“负责什么”的范围内时，补充、修正或移除其中过期的内容。

更新时：

- 只修改与用户请求直接相关的章节。
- 保留仍然有效的规则和证据。
- 新规则必须补充证据来源。
- 如果新内容与已有规则冲突，默认列入待确认项；只有用户明确说明旧规则已废弃、错误或应被替换时，才能修正已有规则。
- 用户明确规则仅能按“用户明确规则的优先级”一节修改或移除；代码不一致只能作为冲突证据报告。
- 如果上下文单元已经关联项目文档，必须同时检查文档；分别记录“已更新”或“已检查，无需修改”。
- 如果本次维护使知识无法继续安全压缩，按 `documentation.md` 给出项目文档建议；用户没有明确要求时不创建文件。

### 内容边界与过期检查

每次向已有上下文单元加入一组新规则前，先判断它是否仍属于同一个加载原因。

- 如果新内容只是同一流程的新增约束、入口或证据，按普通内容维护更新。
- 如果新内容形成可独立触发的页面流程、复用能力、数据契约或产品规则，且后续修改不必加载原单元的主要内容，不把它作为“补充”继续追加；说明应拆分的候选边界。用户明确要求拆分、合并、删除、移动或整理时，再按 `reorganization.md` 输出计划并等待确认。
- 不以行数、规则条数或文件数量作为拆分依据；只以职责边界和加载原因判断。

同时检查本次引用的关键入口与证据：若当前工作树中路径已删除、移动或与规则冲突，不能继续把旧描述写成当前事实。用户明确要求维护时，可以在证据充分的前提下修正或移除已失效事实；无法确认是临时未提交改动还是稳定变更时，写入报告的待确认项，不擅自删除上下文单元。

### 写入项目基础上下文

当知识属于整个项目都需要知道、但不足以形成独立主题的基础事实时，写入：

```text
.agents/skills/ctx-project-baseline/SKILL.md
```

例如：包管理工具、常用命令、前端源码入口或项目级配置入口。

如果该文件不存在，可以创建最小的 `ctx-project-baseline`，只记录当前有明确证据的基础事实。维护报告必须说明：该文件由手动维护创建，项目尚未完成完整初始化。

### 归属歧义

如果多个已有 `ctx-*` 上下文单元都可能负责同一知识，且无法根据职责范围和证据确定唯一归属：

- 不修改多个文件。
- 不凭直觉选择其中一个文件。
- 不新建可能重复的上下文单元。
- 列出候选文件、说明歧义，并等待用户决定。

### 职责边界不匹配

如果已有 `ctx-*` 上下文单元与新知识相关，但新知识不属于该文件“负责什么”的核心范围：

- 不为了避免新建文件而扩张已有上下文单元的职责。
- 不因为共享文件、接口或关键词就认定它们属于同一知识边界。
- 按正常流程判断应创建新的上下文单元、写入项目基础上下文、列入待确认或跳过。
- 如果两个上下文单元需要互相引用，只在各自职责范围内保留最小关联说明。

### 创建新的上下文单元

当没有已有 `ctx-*` 上下文单元负责该知识，且候选知识通过 `selection.md` 的全部判断条件时：

1. 使用 `taxonomy.md` 确定分类、路径和名称。
2. 使用 `documentation.md` 执行安全压缩测试，判断是否需要给出项目文档建议。
3. 使用 `template.md` 创建新的 `ctx-*` 上下文单元。
4. 用户明确要求创建项目文档时，按用户阅读主题选择一个或多个相关 `ctx-*`，创建或复用项目文档并建立双向关联。
5. 用户没有明确要求时，只在维护报告中输出项目文档建议。
6. 不创建与已有主题重复或边界重叠的上下文单元或项目文档。

### 记录待确认事项

只有同时满足以下条件，才能将不确定内容写入已有 `ctx-*` 上下文单元的“待确认事项”：

- 用户明确要求记录该内容。
- 已存在唯一且职责匹配的上下文单元。
- 内容不会改变该文件的 `description`、负责范围或已确认事实。
- 每项均能写明尚未确认的问题、当前证据和仍需确认的信息。

不满足任一条件时，不修改文件，只在维护报告中列入待确认项。

### 列入待确认或跳过

以下情况不创建或更新稳定规则：

- 证据不足、规则冲突或职责边界不清：列入待确认项。
- 普通实现细节、临时逻辑、单次模式或通用前端知识：跳过，并说明原因。

## 手动维护报告

```text
维护结果：
- 已更新：知识项、路径与修改内容
- 已创建：知识项、路径、职责与证据
- 关联项目文档：路径、文档主题、相关上下文单元，以及已更新或已检查无需修改
- 项目文档建议：主题、原因、建议路径和相关上下文单元
- 已记录待确认事项：知识项、路径与仍需确认的信息
- 已检查，无需更新：检查范围与未写入的原因
- 写入项目基础上下文：知识项与事实摘要
- 跳过：知识项与原因
- 待确认：未写入上下文的知识项与无法仅凭现有证据判断的问题
```

实际创建或修改了上下文单元或关联项目文档时，在最终结果中额外输出：`project-context：已更新`。

## 完成前检查

输出结果前确认：

- 用户明确要求了上下文维护，且输入信息足以完成“更新、待确认或无需更新”的判断；只有满足写入条件时才修改文件。
- 对泛化更新请求，已先按“默认处理：先评估，条件写入”逐项判断；没有满足写入条件时，已明确报告“已检查，无需更新”。
- 没有修改非 `ctx-*` 的其他 skill。
- 每条独立知识项均已单独判断处理方式。
- 已有上下文单元能够覆盖且职责边界匹配时，没有创建重复文件。
- 只有相关但职责边界不匹配时，没有扩张已有上下文单元的范围。
- 多个上下文单元可能匹配时，已列入待确认项，未擅自修改。
- 新建上下文单元通过 `selection.md` 的全部判断条件。
- 更新后没有把独立加载原因继续堆入同一上下文单元；需要结构调整的内容已说明但未越权执行。
- 新建或知识深度明显增加的上下文单元已完成安全压缩测试。
