# 手动维护规则

当用户明确要求记录、沉淀、补充、完善、修正、更新、整理或维护前端项目持久化上下文，或明确维护某个 `ctx-*` skill 的内部资源时，按本流程处理。普通代码修改、样式调整、临时调试和泛泛的“注意”不自动触发。

## 默认处理

“更新上下文”“根据 git diff 更新”等泛化请求只授权评估后按需写入。只有候选知识同时具有稳定变化、未来修改价值和可定位证据时才修改；没有满足条件时，结果应为“已检查，无需更新”。

## 范围与边界

本机制只写入 `.agents/skills/ctx-*/` 中属于 `ctx-*` skill 的文件；不维护 `docs/`、非 `ctx-*` skill 或外部项目文档。不得写入敏感值、临时调试信息或未经确认的猜测。

用户明确要求长期记录具体规则时，优先写入唯一职责匹配的既有 skill；用户规则放入“用户明确规则”，保留来源、记录日期和状态。代码与其冲突时只报告冲突，除非用户明确废弃或替换，不能自动改写。

## 处理步骤

1. 读取用户指定的代码、diff、说明及候选 `ctx-*` skill；按知识边界拆分候选项。
2. 查找唯一职责匹配的既有 skill。匹配时只更新相关内容与证据；没有唯一归属时，按 `selection.md` 判断新建、写入 `ctx-project-baseline`、待确认或跳过。
3. 新建 skill 时使用 `taxonomy.md` 和 `template.md`。
4. 新建或明显扩展复杂连续知识时，读取 `references.md`；仅通过准入判断后，创建或更新所属 skill 的内部 reference，并更新 `SKILL.md` 的读取条件。
5. 用户明确要求删除、拆分、合并、重命名、移动或整理 skill 或内部资源时，读取 `reorganization.md`，先输出计划并等待确认。

## 根据 git diff 更新

只在用户明确提出时执行。先读取指定 diff 或变更文件；依据现有 skill 的职责、关键入口与内部资源定位候选。仅当关键入口、跨文件契约、数据语义、流程联动、产品规则或防护约束发生稳定变化时更新。普通实现调整、局部样式变化和无长期知识变化的重命名跳过。

## 报告与完成检查

报告列出：已更新、已创建、内部 reference、写入项目基础上下文、待确认、跳过和已检查无需更新，并给出每项证据。

完成前确认：每项知识有唯一归属；没有扩张职责或新建重复 skill；reference 满足 `references.md` 且有读取条件；每条重要修改有证据；结构调整已获得确认；未修改 `docs/` 或非 `ctx-*` skill。实际写入时输出 `project-context：已更新`。
