# 前端项目持久化上下文

## 目标

为前端项目建立和维护最小、准确且可按需加载的持久化上下文集合。上下文单元只记录具有长期价值、且不容易从单个文件直接看出的项目知识。

## 适用边界

本 skill 只处理三类用户明确请求：

- **初始化**：分析一个前端项目并创建最初的 `ctx-*` 上下文单元。
- **手动维护**：记录、补充、完善、修正或更新已有的 `ctx-*` 上下文单元，必要时创建新的上下文单元；用户明确要求时，也可在确认后删除、拆分、合并、重命名或移动 `ctx-*` 上下文单元，但固定的 `ctx-project-baseline` 仅允许内容维护。
- **审计**：只读检查 `ctx-*` 上下文单元是否过期、重复、误触发、边界不清或存在误导。

本 skill 不处理：

- 普通功能开发或代码修改。
- 代码修改后的自动检查、自动提示或自动更新。
- 后端项目的规则提炼。
- 名称不以 `ctx-` 开头的其他 `.agents/skills/`。
- 没有长期价值的局部实现细节、临时调试信息或未经确认的猜测。

## 所有权边界

- `project-context` 是入口与管理 skill，本身不使用 `ctx-` 前缀。
- 本 skill 只创建和维护 `.agents/skills/ctx-*/SKILL.md`。
- 其他 `.agents/skills/` 目录可以在必要时作为只读参考，但不得创建、修改、移动或删除。

## 按任务读取规则

### 初始化

每次初始化都必须读取：

- `references/selection.md`：判断候选知识是否值得提取。
- `references/taxonomy.md`：确定已选知识的职责边界、目标目录和命名。
- `references/template.md`：按统一模板生成上下文单元。
- `references/initialization.md`：执行前端项目的前置检查、分析和生成流程。

### 手动维护

每次手动维护都先读取：

- `references/maintenance.md`：识别维护意图、查找已有上下文单元，并决定更新、新建、写入项目基础上下文、待确认或跳过。

只有在没有唯一的既有归属、且可能需要创建新上下文单元时，才额外读取：

- `references/selection.md`：判断候选知识是否值得新建上下文单元。
- `references/taxonomy.md`：确定新建上下文单元的职责边界、目标目录和命名。
- `references/template.md`：按统一模板创建新的上下文单元。

如果用户明确要求删除、拆分、合并、重命名、移动或整理 `ctx-*` 上下文单元，额外读取：

- `references/reorganization.md`：分析结构调整影响、输出计划、等待确认并执行已确认的调整。

结构调整涉及拆分、合并、重命名或移动时，按 `references/reorganization.md` 的要求读取 `references/taxonomy.md`；只有需要创建新上下文单元时，才额外读取 `references/template.md`。

如果唯一目标是已有 `ctx-*` 上下文单元，只读取该文件和与本次修改直接相关的证据；不默认加载选择、分类和模板规则。

### 审计

每次审计都必须读取：

- `references/audit.md`：执行只读审计并输出分级结果。
- `references/taxonomy.md`：检查 `ctx-*` 上下文单元的分类、路径和命名是否正确。
- `references/template.md`：检查 frontmatter、职责边界和章节结构是否符合上下文单元模板。

审计只检查直接位于 `.agents/skills/` 下的 `ctx-*` 目录及其 `SKILL.md`，不得在审计过程中修改、删除、拆分或合并任何文件。

## 通用原则

- 用户的明确请求只授权维护 `ctx-*` 上下文单元，不授权覆盖非 `ctx-*` skill。
- 用户明确要求记录时，用户对“是否需要长期保留”的判断优先于 AI 的默认价值判断；具体处理方式遵循 `references/maintenance.md`。
- 是否新建专项上下文单元，必须完全遵循 `references/selection.md`。
- 如果已有 `ctx-*` 上下文单元明确负责该知识边界，优先更新已有文件，不新建重复文件。
- 不因目录存在、模式只出现一次，或代码看起来像最佳实践就创建上下文单元。
- 不创建空文件、通用开发教程、大段源码摘录或重复的权威说明。
- 所有重要结论都要在上下文单元中注明证据来源。
- 证据不足、规则冲突或职责边界不清时，不擅自写成稳定规则，列入待确认项。
