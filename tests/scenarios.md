# 场景回归样例

这些样例用于修改 `project-context` 后检查决策和修改边界，不要求输出固定措辞。规则入口为 [SKILL.md](../.agents/skills/project-context/SKILL.md)。

## 验证方式

每个场景独立运行。在临时目录中准备“输入”描述的最小文件，将用户请求交给待验证的 skill，再对照预期决策和实际 diff。已有规则文件需包含有效 frontmatter、负责范围和样例所需记录。只向执行者提供输入，不把预期结果作为任务指令。

记录最终状态、目标文件、实际变更和完成检查结果。文件写入边界包含创建、修改、移动、重命名和删除；只读场景还应检查文件内容与目录清单是否保持不变。没有执行实际任务时，只能记为规则推演，不能记为行为测试通过。

新增 reference 的示例文件名用于说明主题，可采用含义相同且符合命名规则的名称；既有文件路径按输入保持。

## 1. 项目基础旧记录原地更新

- 输入：`ctx-project-tooling/SKILL.md` 唯一记录“构建前先生成接口类型”。`ctx-project-baseline/SKILL.md` 已存在，但只记录部署限制。项目指令已明确生成命令改为 `pnpm generate:api`。用户请求：“更新上下文中的接口类型生成命令，暂不迁移旧 skill。”
- 预期决策：更新旧记录，目标仍为 `ctx-project-tooling/SKILL.md`。baseline 不属于旧结构。
- 允许修改：仅旧 skill 中的相关命令和证据。不得向 baseline 复制该记录，不得迁移或删除旧 skill。

## 2. 新旧入口存在权威冲突

- 输入：旧 `ctx-project-tooling` 要求从仓库根目录构建，新 `ctx-project-baseline` 要求从子项目构建。两份记录均声称有效，没有替代关系或其他可判定的证据。用户请求：“核对并更新构建上下文。”
- 预期决策：待确认，说明两处权威记录冲突；不能仅因 baseline 是规范名称就优先采用。
- 允许修改：无。在权威位置未确定前，不更新、覆盖或复制相关记录。

## 3. 用户规则与当前代码冲突

- 输入：`ctx-policies` 有用户明确要求保留的有效规则“额度耗尽时允许导出历史结果”，附来源和日期。当前页面却禁用了该入口。用户请求：“根据这次 diff 更新额度上下文。”
- 预期决策：待确认，说明实现与用户规则不一致；不把代码观察当作用户已废弃规则。
- 允许修改：无。保留原规则的内容、来源、日期和有效状态。

## 4. 初始化时筛选基础信息

- 输入：前端项目使用 React，`package.json` 只有常规依赖和 `dev`、`build` 命令；另有项目指令要求“所有前端命令从 `apps/portal` 执行，构建前先运行 `pnpm generate:api`”。生成脚本和前端目录均存在。项目尚无 `ctx-*`。用户请求：“初始化项目持久化上下文。”
- 预期决策：保留工作目录、生成命令及先后约束，创建 `ctx-project-baseline`；跳过仅罗列框架、依赖版本和完整 scripts 的候选。
- 允许修改：仅创建 baseline 的 `SKILL.md`，记录用途和证据。该样例的约束对所有构建任务都适用，不应单独创建 reference，也不预建其他分类。

## 5. 只分析时零写入

- 输入：复用场景 4 的项目证据，但用户请求：“只分析初始化方案，列出候选和目标位置，不要写文件。”
- 预期决策：给出与场景 4 一致的保留判断和拟建位置，明确尚未执行。计划中的路径不应被报告为已创建或断链。
- 允许修改：无，包括不得创建空目录、`SKILL.md` 或 reference。

## 6. 新增主题时同步路由

- 输入：`ctx-integrations` 已记录地图 SDK。项目指令明确“地图截图必须等待 SDK 的渲染完成事件，普通页面就绪事件不代表可截图”；相关调用和测试提供证据。该约束仅用于地图截图任务，尚无相同读取条件的 reference。用户请求：“把地图截图的长期约束补进上下文。”
- 预期决策：新增 `references/map-capture.md`，同步更新 `ctx-integrations/SKILL.md` 的按需读取项。路由明确匹配地图截图和 SDK 渲染完成信号。
- 允许修改：新增的 reference 及所属入口。完成检查须核对路径、直接路由和证据；不改变已有地图主题的权威内容，不修改业务代码。

## 7. ctx-other 的读取条件变化

- 输入：`ctx-other/references/review-evidence.md` 已被确认归入兜底分类，记录前端视觉验收中参考素材的溯源规则。用户补充并确认“交互录屏验收也适用”，证据充分，分类和目标文件无争议。原 description 和路由只覆盖静态截图验收。用户请求：“更新这条规则及其读取条件。”
- 预期决策：更新既有 reference，同时让所属入口的 description 和路由覆盖静态截图、交互录屏验收。
- 允许修改：该 reference 和 `ctx-other/SKILL.md`。完成检查须发现并修正仅改 reference、遗漏任一入口触发条件的情况。

## 8. 结构迁移先规划

- 输入：`ctx-project-tooling` 和 `ctx-project-build` 各有不同的有效工程约束，没有权威冲突；baseline 尚不存在。用户请求：“先给我合并到分类级 skill 的迁移计划，等我确认再执行。”
- 预期决策：识别两个旧 skill，规范目标为 `ctx-project-baseline`。逐项确定保留内容、目标文件和链接处理，不将拟建 baseline 当作旧 skill。
- 允许修改：无。等待确认期间也不得先创建承接迁移内容的 baseline 或 reference。

## 9. 完成检查保护用户已有修改

- 输入：用户已在 `ctx-integrations/SKILL.md` 中补充地图配额限制，尚未提交。随后用户提出场景 6 的请求，且新约束与已有修改不冲突。
- 预期决策：在用户修改的基础上补充地图截图路由，新增对应 reference。完成检查对照执行前状态，保留配额限制，并把新建的未跟踪文件计入变更范围。
- 允许修改：场景 6 的新增内容和关联入口。不得覆盖配额限制，也不得通过还原、清理工作树来通过检查。
