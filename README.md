# 前端项目持久化上下文

## 安装与更新

需要本机已安装 Node.js 和 `npx`。

进入需要使用该 skill 的项目目录后安装。`-y` 会跳过 scope 选择并使用默认的项目级安装：

```bash
npx skills add taoweioo/project-context -y
```

后续在该项目目录中更新：

```bash
npx skills update project-context -p
```

## 项目设想

本项目探索一种面向前端项目 AI 开发的“持久化上下文”机制。

AI 在每次新会话中都不应依赖上一轮对话的记忆。前端项目中复杂、特殊、容易改错，且不容易从当前文件直接看出的知识，应沉淀为可按需加载的项目文件。这样，AI 在修改相关代码时能够获得必要的项目背景，减少重复阅读代码、遗漏约定和重新引入历史问题的风险。

持久化上下文不是完整的项目说明书，也不是代码的重复索引。它只保存对后续前端开发有长期价值的项目知识。复杂知识可以形成项目文档建议；只有用户明确要求时，才创建关联项目文档。

## 适用范围

本项目当前只面向前端项目。

前端项目包含页面、组件、路由、状态管理、接口调用、缓存、样式、权限、表单、文件上传和第三方前端集成等内容。

后端项目暂不在本项目的探索范围内。当前的验证经验和维护精力集中在前端领域，不能对后端架构、数据存储、服务治理、安全和运维规则的上下文质量负责。

## 要解决的问题

- AI 会话之间没有可靠的项目记忆。
- 复杂业务规则、跨文件契约和历史问题通常分散在代码、提交记录和开发者经验中。
- 仅依赖当前任务涉及的文件，容易遗漏路由、缓存、权限、数据参数和调用方之间的联动关系。
- 项目文档过大或过泛时，AI 难以按需找到真正重要的内容。
- 复杂知识只写入 skill 时，不方便用户快速理解业务走向；文档与 skill 分别维护时，又容易出现单向更新和内容冲突。

## 核心概念

### 持久化上下文

项目中需要跨会话保留的前端开发知识。例如：稳定业务规则、跨文件数据契约、关键参数语义、必须联动修改的流程，以及防止重犯历史问题的防护约束。

### 上下文单元

一个独立的 `SKILL.md` 及其相关内容。每个上下文单元只负责一个明确的知识边界，并在相关任务中按需加载。

### 独立承载

知识能够安全压缩为简短、独立的事实与约束时，只使用一个 `ctx-*` 上下文单元承载。

### 关联项目文档

项目文档按业务主题、用户流程或问题域组织，默认用一个以图为优先、与业务关系匹配的主视觉和少量补充信息展示业务全貌。极短的线性过程可使用箭头链，以条件组合为主的知识可使用决策表，不为形式完整强制生成 Mermaid。

一个文档可以关联多个职责清晰的 `ctx-*`；每个 `ctx-*` 最多声明一份主文档。文档统一放在 `docs/project-context/`。

### 初始化上下文

用户主动要求分析一个新前端项目时，AI 根据项目配置、目录结构和高价值代码区域，建立最初的持久化上下文单元。

### 手动维护

只有在用户明确要求创建、更新、审计、同步或重组持久化上下文，或者维护已经关联的项目文档时，AI 才执行上下文维护流程。普通代码任务结束后，不自动检查、不自动提示，也不自动写入上下文。

维护过程中先检查知识边界，再执行安全压缩测试。测试只决定是否给出项目文档建议，不提供创建授权。用户明确要求创建时，再按用户阅读主题组织一个或多个相关上下文单元。

## 应保存的知识

持久化上下文优先保存以下知识：

- 不容易从单个文件直接看出的跨文件契约。
- 多处代码稳定遵循的项目约定。
- 路由、状态、缓存、接口、权限和数据参数之间的联动关系。
- 改错后影响范围较大的业务规则和架构边界。
- 高风险限制、历史问题及其原因。
- 关键入口文件、字段、参数、事件和数据契约的稳定语义。

## 不应保存的知识

持久化上下文不应变成通用开发教程，也不应重复代码本身。以下内容通常不应沉淀：

- 一眼可以从代码看出的组件结构和普通实现细节。
- 大段源码或通用代码模板。
- 临时调试信息。
- 只出现一次且没有稳定证据的实现模式。
- 未经确认的业务猜测。
- 与当前前端项目无关的通用最佳实践。

## 核心原则

- 每个上下文单元只负责一个明确的知识边界。
- 只在相关任务中按需加载，不一次性加载全部项目资料。
- 不使用代码行数、文件数量、规则条数或任意评分判断是否需要项目文档。
- 用户没有明确要求时，不创建项目文档，只在维护报告中给出建议。
- 上下文单元按职责边界拆分，项目文档按用户阅读主题组织，两者不强制使用相同粒度。
- 维护关联项目文档时，必须读取并检查文档和全部关联上下文单元；各文件分别报告已更新或已检查无需修改。
- 关联项目文档只维护面向用户的业务走向；`ctx-*` 继续维护代码入口、精确约束、技术流程、证据和防止错误修改所需的设计原因。
- 每条重要规则都应有代码、项目约定或已确认业务说明作为依据。
- 从局部代码推导出的结论必须标明其证据范围，不能直接写成长期事实。
- 发现边界不清、内容重复或规则冲突时，应先说明问题，再决定是否调整。
- 用户没有明确要求时，不更新持久化上下文。

## 预期使用方式

用户可以主动提出以下类型的请求：

```text
初始化这个前端项目的持久化上下文。

根据这次 git diff 更新持久化上下文。

为订阅生命周期创建一份项目文档，并关联相关持久化上下文。

维护这份关联项目文档，并同步检查它关联的上下文单元。

审计现有持久化上下文是否过期、重复或存在误导。
```

AI 应根据请求，只读取和维护必要的上下文单元，并明确说明判断依据和不确定点。

## 维护可观测性

实际创建或修改持久化上下文及其关联项目文档时，skill 会额外输出一句：

```text
project-context：已更新
```

未写入文件时不输出这句提示。
